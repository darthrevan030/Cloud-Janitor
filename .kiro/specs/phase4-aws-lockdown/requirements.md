# Requirements Document

## Introduction

This specification covers Phase 4 of the Cloud Janitor product backlog (`.kiro/2026-07-08-product-backlog.md`) — "lock down real AWS": SEC-5, INF-2, and DOC-1. These three issues share a common premise: `AWSProvider` (`src/cloud_janitor/mcp_server/backends/aws_provider.py`) is a real, live boto3 provider as of v0.3.0, but nothing in the codebase or documentation defines *how* it should be credentialed in a shared deployment, *what* the minimal permission set for it actually is, or *where* an operator goes to find both answers together with the identity and privacy posture decided in Phase 1.

**Confirmed from the code (not assumed):** `AWSProvider` is read-only. Its three public methods (`get_cost_data`, `get_security_data`, `check_dependencies`) call only `describe_*`/`get_*` boto3 methods — there is no `create_*`, `delete_*`, `modify_*`, `authorize_*`, or `revoke_*` call anywhere in the file. All infrastructure mutation happens via `Orchestrator`'s Terraform subprocess calls (`orchestrator/orchestrator.py`, `approve()` and `_handle_confirm_rollback()`), which apply HCL generated by `RemediationArchitect` (`agents/remediation_architect.py`). This means the read/write architectural split SEC-5 asks for already exists structurally (provider = read, Terraform = write) — what is missing is making that boundary an explicit, separately-credentialed one, and publishing the exact permission set each side needs (INF-2), before writing the guide that ties it together with Phase 1's identity and privacy work (DOC-1).

**Sequencing within this phase:** Requirements 1–2 (SEC-5, credential sourcing and the read/write credential boundary) and Requirements 3–4 (INF-2, the two IAM policy artifacts) are designed together, since the policy artifacts are what the write role in Requirement 2 attaches. Requirement 5 (DOC-1) is written last and depends on Requirements 1–4 of this phase plus Phase 1's SEC-1 (`.kiro/specs/phase1-trust-hardening/design.md`, "Privacy Posture Attestation") and SEC-3 (`.kiro/specs/phase1-trust-hardening/design.md`, "Identity Resolution") — DOC-1 documents reality established by the other four requirements, not aspirational design.

Full technical design is in `design.md` in this folder.

## Glossary

- **AWSProvider**: The boto3-backed `CloudProvider` implementation (`mcp_server/backends/aws_provider.py`) used by the FinOps Auditor and SecOps Guard agents to scan live AWS resources. Confirmed read-only (see Introduction).
- **Orchestrator**: The central coordination module (`orchestrator/orchestrator.py`) that sequences agent execution, manages approval gates, and invokes Terraform `init`/`plan`/`apply` subprocess calls.
- **Read_Role**: The IAM role attached to the EC2 instance profile running Cloud Janitor, resolved ambiently by boto3's default credential chain and used by every `AWSProvider._make_client()` call and by the Phase 1 SEC-3 identity check (`sts:GetCallerIdentity`).
- **Remediation_Role**: A separately-scoped IAM role, distinct from the Read_Role, assumed only for the lifetime of the `terraform init`/`plan`/`apply` subprocess sequence invoked by `approve()` and `_handle_confirm_rollback()`.
- **Instance_Role_Credential_Chain**: boto3's default/ambient credential resolution order (environment variables, shared credentials file, then EC2/ECS instance metadata). An EC2 instance profile is the production-grade member of this chain and requires no code change to `_make_client()` to use.
- **IAM_Policy_Artifact**: A ready-to-attach IAM policy JSON document checked into the repository under `iam/`.
- **Reference_Architecture**: The single shared EC2 instance deployment topology documented in the Deployment_Guide, chosen over an autoscaled/multi-node topology (see Requirement 5.2 for rationale).
- **Deployment_Guide**: The consolidated guide at `docs/deployment.md`.
- **Privacy_Posture**: The per-backend LLM data-retention attestation mechanism designed in Phase 1 SEC-1 (`JANITOR_LLM_RETENTION_POLICY`, `get_privacy_posture()`).
- **Identity_Resolution**: The fail-closed IAM identity verification designed in Phase 1 SEC-3 (`core/identity.py`, `resolve_actor()`), which requires `sts:GetCallerIdentity` to succeed in Real-AWS mode before any approval/rollback proceeds.

## Requirements

### Requirement 1: Instance-Role Credential Sourcing (No Long-Lived Keys)

**User Story:** As a security engineer, I want Cloud Janitor's AWS credentials to come from an EC2 instance role rather than long-lived access keys committed to config or environment files, so that a leaked `.env` or `accounts.json` cannot expose standing AWS credentials.

#### Acceptance Criteria

1. THE Deployment_Guide SHALL document EC2 instance-profile role attachment as the standard credential source for `JANITOR_BACKEND=aws` deployments, and SHALL state that no `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` values are to be set in `.env`, `accounts.json`, or any committed configuration file for production use.
2. THE codebase SHALL require no change to `AWSProvider._make_client()` to support instance-role sourcing: since an attached instance profile is resolved automatically as the lowest-priority, most production-appropriate member of the Instance_Role_Credential_Chain, `boto3.client(service, region_name=..., endpoint_url=...)` picks it up unmodified.
3. IF a deployment sets `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` as static long-lived keys, THEN THE Deployment_Guide SHALL flag this as a non-recommended configuration, permitted only for local development against LocalStack (`AWS_ENDPOINT_URL` set).
4. THE Deployment_Guide SHALL document the minimum EC2 instance-role trust policy (the EC2 service principal, `ec2.amazonaws.com`) required to attach the Read_Role to an instance profile.

### Requirement 2: Separately-Scoped Remediation Credentials for Terraform Apply

**User Story:** As a security engineer, I want the `terraform apply` subprocess to run under a separately-scoped write role rather than the same ambient credentials used for read-only audit scans, so that a compromised or over-permissioned audit process cannot mutate infrastructure.

#### Acceptance Criteria

1. THE Orchestrator SHALL provide a function `_assume_remediation_role() -> dict[str, str] | None` that, WHEN the `JANITOR_REMEDIATION_ROLE_ARN` environment variable is set, calls `sts:AssumeRole` against that ARN and returns a dict containing `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` populated from the returned temporary credentials.
2. WHEN `Orchestrator.approve()` or `Orchestrator._handle_confirm_rollback()` builds the environment for its `terraform init`/`plan`/`apply` subprocess calls AND `JANITOR_REMEDIATION_ROLE_ARN` is set, THE Orchestrator SHALL call `_assume_remediation_role()` and use its returned credential keys to override any ambient `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN` values already present in the `_build_subprocess_env("terraform")` result for that call only.
3. IF `JANITOR_REMEDIATION_ROLE_ARN` is unset, THEN THE Orchestrator SHALL fall back to today's behavior (ambient credentials for the terraform subprocess) AND SHALL log a WARNING once per process lifetime stating that the read/write credential boundary is not configured.
4. IF `sts:AssumeRole` fails (access denied, invalid ARN, expired or misconfigured trust policy), THEN THE Orchestrator SHALL NOT execute `terraform init`, `plan`, or `apply`, SHALL return a failure result identifying that remediation credentials could not be obtained, and SHALL write an audit entry with action `"remediation_role_assumption_failed"`.
5. THE credential injection in criterion 2 SHALL be scoped strictly to the `terraform`-kind subprocess environment used by the `init`/`plan`/`apply` sequence in `approve()` and `_handle_confirm_rollback()`. The pre/post-remediation hook subprocess environment (`_build_subprocess_env("hook")`) SHALL remain unchanged by this requirement.
6. THE Orchestrator SHALL NOT cache or reuse temporary credentials from `_assume_remediation_role()` across separate `approve()`/`_handle_confirm_rollback()` invocations; each invocation that needs write access SHALL call `_assume_remediation_role()` fresh.

### Requirement 3: Least-Privilege Read-Only IAM Policy Artifact

**User Story:** As a cloud security reviewer, I want a ready-to-attach IAM policy scoped to exactly the AWS API actions the audit/scan path calls, so that I am not asked to approve a broad, unscoped permission set to onboard the tool.

#### Acceptance Criteria

1. THE repository SHALL contain an IAM_Policy_Artifact at `iam/janitor-read-policy.json` granting exactly the following actions, each verified against an actual `_make_client(...).<method>()` or `.get_paginator("<method>")` call site in `aws_provider.py`: `ec2:DescribeVolumes`, `ec2:DescribeInstances`, `ec2:DescribeSecurityGroups`, `ec2:DescribeNetworkInterfaces`, `elasticache:DescribeCacheClusters`, `elasticache:DescribeReplicationGroups`, `cloudwatch:GetMetricStatistics`.
2. THE `iam/janitor-read-policy.json` SHALL additionally grant `sts:GetCallerIdentity` (consumed by Phase 1 SEC-3's Identity_Resolution) and `sts:AssumeRole` scoped via `Resource` to the Remediation_Role ARN, to support Requirement 2's role-assumption flow.
3. FOR each action in `iam/janitor-read-policy.json` for which the AWS API does not support resource-level IAM permissions at all (every `ec2:Describe*` action, `cloudwatch:GetMetricStatistics`, and `sts:GetCallerIdentity`), THE statement's `Resource` element SHALL be `"*"`, and the design documentation (not the policy JSON itself, which has no native comment syntax) SHALL state explicitly, action by action, that this is because AWS provides no resource-level permission support for that action — not because the statement was left unscoped by omission. `elasticache:DescribeCacheClusters` (resource type `cluster`) and `elasticache:DescribeReplicationGroups` (resource type `replicationgroup`) ARE documented by AWS as supporting resource-level permissions — for these two actions specifically, `Resource` MAY still be `"*"`, but the design documentation SHALL justify that choice as operational simplicity (specific resource IDs are unknown ahead of an account-wide scan), never as an AWS scoping limitation that does not actually exist for these actions.
4. THE `iam/janitor-read-policy.json` SHALL NOT include any action matching `Create*`, `Delete*`, `Modify*`, `Put*`, `Authorize*`, `Revoke*`, `Attach*`, `Detach*`, or `Update*` for the `ec2` or `elasticache` service prefixes.
5. THE repository SHALL provide an automated test that parses `aws_provider.py`'s source for boto3 method calls following a `_make_client(...)` assignment and asserts that every such method name (mapped to its `service:Action` form) is present in `iam/janitor-read-policy.json`, so the policy cannot silently drift from the code it is meant to cover.

### Requirement 4: Least-Privilege Remediation IAM Policy Artifact

**User Story:** As a cloud security reviewer, I want a ready-to-attach IAM policy scoped to exactly the AWS actions Terraform needs to apply the Remediation Architect's generated HCL, so that the write path is not granted broader permissions than its five known remediation templates require.

#### Acceptance Criteria

1. THE repository SHALL contain an IAM_Policy_Artifact at `iam/janitor-remediation-policy.json` whose action list is derived exclusively from the resource types and `local-exec` provisioner commands actually emitted by `RemediationArchitect`'s template methods (`_remediation_ebs_waste`, `_rollback_ebs_waste`, `_remediation_security_group`, `_rollback_security_group`, `_remediation_elasticache_waste`, `_rollback_elasticache_waste`) in `agents/remediation_architect.py`. The two encryption-finding templates (`_remediation_ebs_encryption`, `_remediation_elasticache_encryption`) emit only commented-out HCL and SHALL contribute zero actions.
2. FOR each action in `iam/janitor-remediation-policy.json` for which the AWS API supports resource-level IAM permissions (EBS volume and snapshot actions, security-group-rule actions, ElastiCache cluster and snapshot actions), THE statement's `Resource` element SHALL be scoped to the specific ARN pattern for that resource type (e.g. `arn:aws:ec2:*:*:volume/*`, `arn:aws:ec2:*:*:snapshot/*`, `arn:aws:ec2:*:*:security-group/*`, `arn:aws:ec2:*:*:security-group-rule/*`, `arn:aws:elasticache:*:*:cluster:*`, `arn:aws:elasticache:*:*:snapshot:*`) rather than `"*"`. `ec2:AuthorizeSecurityGroupIngress` and `ec2:RevokeSecurityGroupIngress` SHALL be granted against BOTH the `security-group` and `security-group-rule` ARN patterns — not because AWS unconditionally requires the `security-group-rule` resource type for these actions (AWS's Service Authorization Reference lists `security-group-rule` as an OPTIONAL resource type for these two actions, with a documented footnote that policies using the `security-group-rule` resource-level permission are enforced only when the API request includes `TagSpecifications`, which this codebase's calls do not use — see `agents/remediation_architect.py:358-398`), but for forward-compatibility and defense-in-depth, in case a future change adds `TagSpecifications`-based tagging to these calls, or AWS's enforcement of this optional resource type differs from documented expectations in practice.
3. FOR each action in `iam/janitor-remediation-policy.json` for which the AWS API does not support resource-level IAM permissions at all (`ec2:Describe*`, `sts:GetCallerIdentity`), THE statement's `Resource` element SHALL be `"*"`, with the same action-by-action justification requirement as Requirement 3.3. `elasticache:DescribeCacheClusters`, `elasticache:DescribeSnapshots`, and `elasticache:ListTagsForResource` ARE documented by AWS as supporting resource-level permissions (resource types `cluster`, `snapshot`, and multiple resource types respectively); `Resource: "*"` MAY still be used for these in the state-refresh statement, but the design documentation SHALL justify this as operational simplicity, not as a nonexistent AWS scoping limitation, per the same correction as Requirement 3.3.
4. THE design documentation SHALL note explicitly that the `null_resource` + `local-exec` provisioners used by the EBS-waste and ElastiCache-waste templates invoke the AWS CLI (`aws ec2 delete-volume`, `aws elasticache create-snapshot`, `aws elasticache delete-cache-cluster`) using the same subprocess-inherited credentials as the Terraform AWS provider itself (the Remediation_Role from Requirement 2) — IAM cannot distinguish an action invoked through the Terraform provider from the identical action invoked through an embedded CLI command, so `iam/janitor-remediation-policy.json` SHALL cover both invocation paths under one policy, not two.
5. THE repository SHALL provide an automated test that, for every action in `iam/janitor-remediation-policy.json`, checks the action's service-prefix and verb against a hardcoded reference table of AWS actions known to support resource-level permissions, and fails if a scopable action is granted with `Resource: "*"`.
6. BEFORE `iam/janitor-remediation-policy.json` is considered complete and ready to merge, IT SHALL be validated against either (a) a real (even minimal, single-account, cost-controlled) AWS test account, by actually running the Terraform HCL generated by each of `RemediationArchitect`'s six live-mutation template methods under a role scoped to exactly this policy, or (b) at minimum, an `iam:SimulateCustomPolicy` dry run covering every action/resource pair in the policy. THIS validation SHALL NOT be satisfied by LocalStack-based tests alone: LocalStack does not enforce IAM and structurally cannot detect a missing required resource type (e.g. a write action requiring both the `security-group` and `security-group-rule` ARN patterns, where omitting either causes a real-AWS `AccessDenied` that LocalStack would never surface).

### Requirement 5: Consolidated Enterprise Deployment Guide

**User Story:** As an operator standing up a shared Cloud Janitor deployment, I want one document covering EC2 setup, identity, least-privilege IAM, and LLM egress posture, so that I do not have to reconstruct the shared-deployment story from README fragments, `docker-compose.pro.yml`, and separate phase specs.

#### Acceptance Criteria

1. THE repository SHALL contain `docs/deployment.md` (no `docs/` directory exists prior to this requirement) covering, at minimum, four sections: EC2 setup, identity/auth, least-privilege IAM roles, and BYO-endpoint/privacy posture.
2. THE EC2 setup section SHALL document a single shared EC2 instance as the sole Reference_Architecture, explicitly stating that an autoscaled/multi-node topology is out of scope because no autoscaling infrastructure exists anywhere in the codebase — the same YAGNI reasoning `.kiro/specs/phase2-persistent-state/requirements.md` applies when choosing a single-shared-host SQLite `StateStore` over Postgres/Redis.
3. THE identity/auth section SHALL state that the deployment MUST run under an EC2 instance role (Requirement 1), not developer/static credentials, and SHALL reference Phase 1 SEC-3's Identity_Resolution (`.kiro/specs/phase1-trust-hardening/design.md`) as the mechanism that makes this operationally meaningful: a fail-closed `sts:GetCallerIdentity` check that refuses to proceed in Real-AWS mode without a verifiable identity.
4. THE least-privilege IAM section SHALL embed or link both `iam/janitor-read-policy.json` (Requirement 3) and `iam/janitor-remediation-policy.json` (Requirement 4), and SHALL document the Read_Role / Remediation_Role two-role split from Requirement 2, including the `JANITOR_REMEDIATION_ROLE_ARN` environment variable and the Remediation_Role's trust policy (must trust the Read_Role's ARN as principal).
5. THE BYO-endpoint/privacy posture section SHALL reference Phase 1 SEC-1's Privacy_Posture attestation (`JANITOR_LLM_RETENTION_POLICY`, `get_privacy_posture()`) and SHALL NOT duplicate the existing "Security Hardening" content already in `README.md:392-420` (subprocess isolation, output redaction, hook validation, dashboard binding, Docker socket risk) — it SHALL link to that section instead.
6. THE `docs/deployment.md` file SHALL be written and merged only after Requirements 1–4 of this phase are implemented, so that it documents actual behavior (working `JANITOR_REMEDIATION_ROLE_ARN` support, real policy files on disk) rather than aspirational design.
7. Phase 1's SEC-1 and SEC-3 designs are, as of this phase's authoring, not yet implemented (`phase1-trust-hardening`'s `tasks.md` has zero checked tasks). Where Requirement 5.3/5.5 reference Phase 1 behavior that has not yet shipped, `docs/deployment.md` SHALL describe it as "designed, pending implementation" rather than asserting shipped behavior. THIS phase's `tasks.md` SHALL track, as an explicit non-initial-wave follow-up task, updating that wording to describe actual shipped behavior once `phase1-trust-hardening` ships — see this phase's `tasks.md` for the tracked task and the corresponding cross-reference added to `phase1-trust-hardening/tasks.md`.
