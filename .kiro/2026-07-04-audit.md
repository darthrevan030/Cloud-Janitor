## CRITICAL — Will Crash or Produce Wrong Results

### 1. All AI agents bypass the retry-capable `call_llm()` wrapper

**Files:** `drift_detector.py`, `explainer.py`, `policy_suggester.py`, `anomaly_detector.py`, `incident_policy_generator.py`, `query_interpreter.py`, `tagger.py`

Every AI agent calls `client.chat.completions.create()` directly instead of using the `call_llm(client, ...)` wrapper from `core/llm_client.py`. The wrapper provides exponential backoff, retry on transient errors (429, 500-504), and timeout handling. Without it, a single 429 from OpenRouter crashes the agent (the graceful fallback catches it, but the retry logic is simply never invoked). The `call_llm` function was carefully written with retry logic but is **never used anywhere in the codebase**.

**Impact:** Under load or rate limiting, all AI features fail on first attempt instead of retrying up to 3 times.

**Fix:** Replace all `client.chat.completions.create(...)` calls with `call_llm(client, ...)` and pass the same kwargs.

### 2. `MultiAccountOrchestrator._audit_account()` accesses wrong attribute names

**File:** `src/cloud_janitor/agents/multi_account_orchestrator.py`, line ~216

```python
orch._finops._findings_store_path = findings_store_path
orch._secops._findings_store_path = findings_store_path
orch._architect._findings_store_path = findings_store_path
```

But the actual attribute on `FinOpsAuditor`, `SecOpsGuard`, and `RemediationArchitect` is `self.findings_store_path` (public, no leading underscore). This assignment creates a *new* private attribute that's never read by any of those classes. The actual `self.findings_store_path` remains pointed at the shared default path.

**Impact:** Multi-account audits ALL write to the same `findings_store.json`, corrupting each other. The feature is completely broken.

**Fix:** Change to:

```python
orch._finops.findings_store_path = findings_store_path
orch._secops.findings_store_path = findings_store_path
orch._architect.findings_store_path = findings_store_path
```

### 3. `DriftDetector` compares findings by `(resource_id, check_type)` but FinOps findings don't have `check_type`

**File:** `src/cloud_janitor/agents/drift_detector.py`, `_finding_keys()`:

```python
rid = f.get("resource_id", "")
ct = f.get("check_type", "")
if rid and ct:
    keys.add((rid, ct))
```

FinOps findings use `category: "waste"` and have no `check_type` field. They get `ct = ""` which fails the `if rid and ct` check, making all FinOps findings invisible to drift detection.

**Impact:** Drift detection for cost-waste findings is silently a no-op. New or resolved waste resources are never reported in drift narratives.

**Fix:** Use `category` as fallback key:

```python
ct = f.get("check_type", "") or f.get("category", "")
```

### 4. `Orchestrator.execute_natural_language_audit()` mixes raw resources with findings

**File:** `src/cloud_janitor/orchestrator/orchestrator.py`, lines ~590-612:

```python
cost_findings = list(all_resources)  # ← raw resource dicts assigned as "findings"
...
all_findings = cost_findings + security_findings
```

`get_cost_data()` returns raw resource records (with fields like `id`, `type`, `idle_days`). These are NOT findings (which have `resource_id`, `resource_type`, `severity`, `agent`, etc.). The `all_findings` list becomes a mix of incompatible schemas.

**Impact:** NL audit findings have wrong schema; savings tracking, drift detection, and anomaly filtering all break on NL audit results.

**Fix:** Either run `_finops.scan()` filtered by the NL params, or transform raw resources into proper finding dicts before mixing them.

### 5. `post-remediation.sh` PROJECT_ROOT resolves one level too high

**File:** `hooks/post-remediation.sh`:

```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
PROJECT_ROOT="$(cd "$SCRIPT_DIR/../.." && pwd)"
```

The script lives at `<project_root>/hooks/post-remediation.sh`. Going `../..` from `hooks/` goes to the **parent of the project root**. Should be `$SCRIPT_DIR/..`.

**Impact:** The audit log entry from the post-remediation hook is written to `<parent_of_project>/audit.log` — the wrong location.

**Fix:**

```bash
PROJECT_ROOT="$(cd "$SCRIPT_DIR/.." && pwd)"
```

## HIGH — Logic Errors and Safety Violations

### 6. `Orchestrator.approve()` runs `terraform apply` on ALL resources at once

**File:** `src/cloud_janitor/orchestrator/orchestrator.py`, approve method:

```python
apply_result = subprocess.run(
    [self._tf_cmd, "apply", "-auto-approve"],
    cwd=str(self.output_dir),
)
```

The `output/remediation.tf` contains combined HCL for ALL unblocked findings. When you approve a single resource (`APPROVE vol-abc123`), it runs `terraform apply` on the ENTIRE `remediation.tf` — remediating ALL resources, not just the approved one.

**Impact:** Approving one resource silently remediates all other resources without their own explicit approvals. This violates the human-in-the-loop safety requirement.

**Fix:** Before apply, write only the approved resource's HCL to a temporary working directory and apply that isolated config.

---

### 7. `Orchestrator.__init__` calls `_validate_tf_cmd()` unconditionally

**File:** `src/cloud_janitor/orchestrator/orchestrator.py`:

```python
self._tf_cmd = _validate_tf_cmd()
```

This crashes with `RuntimeError` if neither `tflocal` nor `terraform` is on PATH — even for operations that never need terraform (like `cloud-janitor scan --finops`).

**Impact:** The tool is unusable for pure scanning/auditing on machines without terraform installed.

**Fix:** Lazy-validate `_tf_cmd` only when it's actually needed (in `approve()` and `rollback()` methods).

---

### 8. `_run_pre_remediation_hook_full()` uses hardcoded `"bash"` instead of `BASH_CMD`

**File:** `src/cloud_janitor/orchestrator/orchestrator.py`, line ~919:

```python
result = subprocess.run(
    ["bash", _to_bash_path(hook_path), _to_bash_path(rollback_path)],
    ...
)
```

The sibling method `_run_pre_remediation_hook()` correctly uses `BASH_CMD` (which resolves Git Bash on Windows). This method uses bare `"bash"` which may hit the WSL wrapper on Windows.

**Impact:** On Windows, this alternate hook execution path resolves the wrong bash binary.

**Fix:** Replace `"bash"` with `BASH_CMD`.

## MEDIUM — Correctness Issues

### 9. `SecOpsGuard.check_encryption()` double-fetches security data

**File:** `src/cloud_janitor/agents/secops_guard.py`, `scan()`:

```python
enc_findings_cache = self.check_encryption("elasticache")
enc_findings_ebs = self.check_encryption("ebs")
```

Each call internally calls `get_security_data(check_type="encryption")`, making two identical API/fixture fetches. Additionally, any encryption finding on a resource whose ID doesn't start with `cache-`/`vol-` or contain those substrings is silently dropped by `_determine_resource_type()`.

**Impact:** Performance waste (double fetch in AWS mode), and unclassifiable encryption findings are silently dropped.

### 10. `SavingsTracker._read_findings_store()` has no error handling

**File:** `src/cloud_janitor/agents/savings_tracker.py`:

```python
def _read_findings_store(self) -> dict:
    content = self._findings_store_path.read_text(encoding="utf-8")
    return json.loads(content)
```

If `findings_store.json` doesn't exist (first run, clean state), this raises `FileNotFoundError` which propagates up. The orchestrator's try/except catches it, but the error message is confusing.

**Impact:** First-run approval after a clean state causes opaque savings tracking error.

**Fix:** Add try/except returning empty store dict on missing file.

### 11. Schema validator doesn't recognize `ec2` resource type

**File:** `src/cloud_janitor/agents/schema_validator.py`:

```python
VALID_RESOURCE_TYPES = {"elasticache", "ebs", "security_group"}
```

FinOps generates findings with `resource_type: "ec2"`. The validator rejects these as invalid.

**Impact:** Schema validation flags legitimate EC2 findings as schema errors.

**Fix:** Add `"ec2"` to `VALID_RESOURCE_TYPES`.

### 12. No resource_id validation in `_handle_confirm_rollback()`

**File:** `src/cloud_janitor/orchestrator/orchestrator.py`:

```python
resource_id = command[len(prefix):]
if not resource_id:
    return ...
```

Unlike `_extract_resource_id_from_command()` which validates against `_RESOURCE_ID_PATTERN`, the confirm-rollback handler does no regex validation before using the ID in file path operations (`self.rollbacks_dir / f"{resource_id}.tf"`).

**Impact:** Theoretical path traversal via crafted input. Mitigated by the two-step flow (ROLLBACK must precede CONFIRM ROLLBACK, and ROLLBACK does validate), but defense-in-depth is missing.

### 13. `DriftDetector` narrative generation has no retry

**File:** `src/cloud_janitor/agents/drift_detector.py`:

The LLM call for narratives uses `client.chat.completions.create()` directly without the retry wrapper. Combined with bug #1, a single transient 429 means you never get a narrative.

**Impact:** Under any OpenRouter load, drift narratives always fall back to deterministic text.

---

### 14. `Orchestrator.execute_audit()` redundantly re-fetches cost/security data

**File:** `src/cloud_janitor/orchestrator/orchestrator.py`, `_gather_resources()`:

After agents have already called `get_cost_data()` and `get_security_data()`, the orchestrator calls them again for anomaly detection. In AWS mode, this makes 4 redundant API calls per audit.

**Impact:** Unnecessary AWS API usage and latency; could hit rate limits.

**Fix:** Pass the already-fetched data forward instead of re-fetching.
